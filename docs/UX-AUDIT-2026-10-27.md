# UX audit — 27 October 2026

Seven dimensions read the code; each dimension's findings were then handed to a
separate agent told to refute them. 74 survived, 15 were refuted. What follows
is the synthesis, and it is the source for the A/B drawings on the design
canvas (`https://claude.ai/artifact/AJAue4jSNbmZmjiQrtVvFN`, the eight rows
below the milestone-label row).

Nothing here is a decision. Each theme carries A, the conservative fix, and B,
what a tool that took the problem seriously would do, with a recommendation.
The owner chooses.

**Already fixed, from theme 1:** `snapDelta` quantised to the view scale, so on
the shipped document every drag under a fortnight committed nothing and the bar
sprang back; and the drag preview drew the raw pointer delta while only the
commit snapped. Both landed in `fix(drag): make dragging a bar actually move
it`. The rest of theme 1 is still open.

## 1. The canvas does not answer the pointer

**Root cause.** The whole gesture layer is one hook, `src/app/useChartInteractions.ts`, and three independent things in it are wrong at once: `handleWindowMove` is `useCallback`'d with an empty dependency array (:501) so it keeps render 1's `rowGutterWidth` (120) forever while the live value is 200; `snapDelta` (src/utils/snap.ts:4-17) quantises every drag to the *view scale*, so at the shipped `scale: 'month'` (src/utils/sample.ts:181) a 1-14 day drag commits zero; and the drag preview is built from the raw delta at :421/:475-499 while only the commit at :544 snaps. Nothing hovers (src/styles/global.css:673-674 brightens a `fill="transparent"` rect), nothing cancels (no keydown in `attachWindowListeners`, :677-692), and the drag only ever touches `state.targetId` so the rest of the selection stays put.

**Absorbs:** snap quantised to view scale (blocking/every-session) · gutter + scrollY + stale-layout offsets on dependency, marquee and axis-sweep drags (blocking/every-session) · preview ignores snap, bars jump up to 15 days on release · hover applied to the invisible hit rect · Escape cannot cancel a drag (and makes it worse by clearing the selection while the commit still lands) · dragging one bar ignores the marquee selection · resize handles hidden under the 10px connector dots · bars under 10px covered end to end by their own handles · a bar cannot be dragged to another row (the only path is a flat 40-item `<select>`) · double-click on a bar can never fire (`TaskBars.tsx:233`, the `<g>` has no geometry and its only child is `pointerEvents:'none'`) · the marquee always clears first, so a selection cannot be built in two sweeps.

**Why this is number one.** The app has one verb: drag a bar. On the document it ships with, that verb does nothing for any move under 15 days, the rubber band lands 80px right of the cursor, the bar jumps on release, nothing lights up under the pointer, and Escape does not get you out. Everything else here is a missing feature; this is the advertised feature not working. A planner forms a verdict in the first thirty seconds.

**Choice.**
- **A — Fix the arithmetic.** One `geomRef` assigned `{gutter, axisH, scrollY, layout}` on every render, read by all three handlers (kills all four stalenesses at once). Cap the snap unit at 7 days (`scale === 'day' ? 1 : 7`). Compute the snapped delta inside `handleWindowMove` so preview and commit cannot disagree. `className` on the wrapping `<g>` plus two CSS rules for hover. A keydown in `attachWindowListeners` that nulls `dragRef`. Capture every selected item's originals at mousedown and apply one delta to each. Dots to `cx = x ± 6`, `HANDLE_W` 8 clamped to `width/3`. Move `onDoubleClick` onto the hit rect.
- **B — One gesture layer with real chrome.** A single `clientToChart()` on that ref, used by press, move, drop-test and overlay render (delete the six hand-rolled subtractions). Snap to *dates that exist* — other bars' starts and ends, milestone dates, marker dates, bracket edges, today — collected at mousedown, nearest within 6px, with a vertical guide drawn beside the lasso rect. A follower readout showing previewed start → end and the day delta. `commitDrag` / `abortDrag` as one pair, so Escape, right-click and window blur all abort. Row change as the vertical component of the move, with the target row band highlighted.
- **B costs** what A does not: a live layout inside the drag (so A's `geomRef` is a prerequisite, not an alternative), a candidate-index rebuilt per gesture, two new overlay renderers, and the magnet toggle changes meaning from on/off to free-vs-snap, which needs a line in the shortcuts overlay.
- **Recommend B, with A's `geomRef` landed first**, because candidate snapping is the only version of "snap" that a planner can predict, and the week-quantum in A still throws a bar three days off the milestone they aimed at.

**draw_a.** One artboard, light theme, a 1240×620 chart. Left gutter 200px listing seven group rows in bold with colour spines and their packages indented: "Requirements & architecture / Stakeholder requirements / System architecture", then "Software architecture", "Platform — BSW and MCAL / BSW configuration / MCAL port", "Functional safety, ISO 26262 / ASIL-B FMEDA". ## 2. The chart is a window, not a sheet

**Root cause.** There is exactly one SVG and it is sized to the on-screen client box (`ChartArea.tsx:169-170`, no `viewBox`), with exactly one clip (`chart-clip`, :233-235) that constrains x only — and that clip is referenced from a group whose own transform is `translate(gutter, AXIS_TOTAL_H - scrollY)` (:238), so its top edge *rises with the scroll* instead of staying at the axis. Two more scrolled groups (Rows :212, RowGutter :222) carry no clip at all. The axis is painted before the body, so the body wins paint order. And both export paths clone that same live node (`fileIo.ts:201-243`), inheriting its window height and its current scroll.

**Absorbs:** scrolled rows paint over the axis (blocking/every-session, two findings, one root) · row labels and separators slide into the strip above the gutter · every export and print is cropped to roughly the top 18 of 40 rows, cut mid-row, with no "continues" mark · the print theme at `global.css:170-196` is reachable only by typing it in the palette and no `beforeprint`/`afterprint` applies it · marker labels and the TODAY pill live inside the scrolled group and leave the screen · the last row and a half sit permanently under 52px of floating chrome, so "C-sample build" can never be brought into view · long row names are unclipped and untruncated and run under the bars.

**Why #2.** The sample is 40 rows / 1656px of sheet in a ~700px window, so `maxScroll` is ~1012px and the first wheel notch smears bars, labels, dependency lines and the TODAY pill across the month and week bands. The calendar header is the thing the design nominates as the chart's strongest element (`TimeAxis.tsx:7-16`) and the most ordinary gesture in the app destroys it — then bakes the damage into the PNG that goes to management, which is also missing the bottom 22 rows.

**Choice.**
- **A — Add the clips that are missing and render exports off-screen.** A second `clipPath` in absolute coordinates (`y = AXIS_TOTAL_H`), wrapping all four scrolled groups in one untranslated `<g>`; an x-only gutter clip plus `truncateToWidth` + `<title>` on row labels; move the `<TimeAxis>` block to paint last; `CHROME_H = 52` subtracted from `maxScroll`. For export, reuse the pattern that already exists at `scripts/gen-visual-spec.ts:36-41`: call `layoutDocument`, mount the real sub-renderers into a detached SVG of height `AXIS_TOTAL_H + layout.chartHeight` with `scrollY` forced to 0, serialise that. Print sets `[data-theme='print']` and restores it on `afterprint`.
- **B — Two surfaces: a frozen-pane viewport and a paginated sheet.** On screen, a header layer (axis, TODAY, marker flags, off-screen direction arrows) and a gutter layer painted *over* an explicitly clipped body, with a corner cell where they meet. For output, a sheet renderer independent of the window: `@page` landscape, pagination that repeats the gutter and the axis band on every page, and a title block with the document title and as-of date.
- **B costs** a second renderer entry point and print CSS nobody owns yet; and the sheet half brushes DECISIONS.md D4, which parks presentation export ("Do not build export speculatively") — so B must be raised as *making the existing print path whole*, not as a new deck feature.
- **Recommend A for the screen, A for export.** The off-screen render is the whole fix and it already has a precedent in the repo; frozen panes can wait until someone asks for a corner cell.

## 3. There is no place that lists the plan, and one bar that edits it

**Root cause.** The left column lists rows (`RowGutter.tsx:99-119` draws `row.label` and nothing else) and the bottom bar edits whatever single thing is selected (`SelectionGroup.tsx`). Nothing in the product enumerates tasks, milestones, brackets or markers as objects, so every per-object capability has to be reached by finding its glyph on the canvas — and anything without a glyph, or whose glyph is not hit-testable, is unreachable. This is the owner's own report, twice: *the bottom toolbar is not made for editing tasks.*

**Absorbs:** no way to find a task by name (the palette invites it and indexes nothing) · the gutter rename edits `row.label` while the chart draws `t.label`, and the sample writes the same string into both so 27 packages are printed twice in one chart, 33 are renameable in a place that does not rename them · milestone and bracket names cannot be renamed anywhere, and `ChartContextMenu.tsx:214` says "Edit label" and only sets the selection · a marker, once created, cannot be selected, renamed, re-dated or deleted — `Markers.tsx` emits no `data-pp-kind`, so three handlers that depend on a selected marker are dead and `SelectionGroup.tsx:52` would return `null` anyway · a multi-selection can only be bracketed or deleted, although every withdrawn control already takes an id and a patch · no bulk recolour, though colour *is* the stream tag (D6) · a dependency can only be created by dragging between two 10px dots, and existing ones can only have their *type* changed, not their endpoints · dependency arrows have one fixed elbow and four of the sample's six already route backwards through their own predecessor · the Edit popover has no exit while the caret is in one of its fields (Escape bails at `useKeyboardShortcuts.ts:19` for every control it contains) · no owner field exists on `Task`, and nothing reads several items' dates as text.

**Choice.**
- **A — Complete the bottom bar.** `MultiFields` gains the colour palette, ±1d, ±10% and the row select when the selection is one kind, each applying through one `applyBatch(ops,'user')`. `editStore` generalises from `editingTaskId` to `{kind,id}` and `InlineLabel` mounts in `Milestones.tsx` and `Brackets.tsx`, so the three dead "Edit label" items become real. A `MarkerFields` branch plus a transparent hit line in `Markers.tsx`. A "Depends on" field in the Edit popover modelled on the `RowSelect` that already works, listing predecessors and successors with a remove button. The popover gets `ContextMenu`'s dismissal (outside-mousedown + Escape with `stopPropagation` + a close X). `owner?: string` on `Task` with a text field. Plan items appended to the palette as a "Go to" group so search finds them.
- **B — A left panel that lists the plan.** The column becomes one line per task and milestone under its group, with name, start, end, duration, percent and owner as editable text columns; a filter box at its head narrows the list and the chart follows the highlight; arrow keys walk it; checkbox/shift-range multi-select writes a field to every selected item with "—" where values differ; a detail area at the foot always shows the selection, so there is nothing to open and nothing to dismiss; drag a line onto another group to re-file it. The bottom bar keeps only genuinely one-press actions.
- **B costs**: the layout engine stacks several bars per row via `subRow` (`engine.ts:88-151`), so the panel has to render per-bar lines *inside* a row band; `RowGutter`, the row context menu, selection semantics and `sample.ts` all move with it; and it is the one change here that cannot be shipped in pieces.
- **Recommend B.** A — "put more buttons in the floating bar" — is the thing the owner has already rejected twice, and it still leaves the planner hunting a 2px glyph to answer "when does the HIL campaign finish". B is the shape the content needs: 40 lines of structured data want a list.

## 4. Undo is spent on characters, not on actions

**Root cause.** Every mutator goes through `mutate` → `pushHistory`, one frame per call (`documentStore.ts:99-120`), with `HISTORY_LIMIT = 100` (:6). Continuous inputs are wired straight to the store — the notes textarea on every keystroke (`SelectionGroup.tsx:227`), the percent `type="range"` on every value it passes through (:214-220), the title input on every change (`Header.tsx:111`) — and every multi-item path loops instead of batching. `applyBatch` (documentStore.ts:149-152) already makes a batch one frame and is the *agent's* path, required by SRS-ABR-013 so "one user keystroke must be able to revert an agent's entire turn".

**Absorbs:** typing a 120-character note evicts the session's whole history (blocking/every-session) · the percent slider does the same per drag · a multi-selection Delete or arrow-nudge costs one frame per item, across four separate loops (keyboard delete, keyboard nudge, `SelectionGroup` Delete, palette Delete) · a plain click on a bar already spends a frame on a zero-delta move · `setDocument` clears `past` and `future`, so Open and Apply-template are outside undo by construction.

**Why #4.** Undo is the only recovery this app has — there is no crash recovery in a saved file (theme 5) and most of the canvas defects above are silent wrong edits. Slipping a 12-package stream by two weeks is 24 Ctrl+Z, and four such gestures evict everything older, so Monday's edits are not undoable by Wednesday. The agent gets the behaviour the user does not.

**Choice.**
- **A — Buffer the four continuous inputs, batch the four loops.** Local `useState` on title, notes and the range input, committing on blur / Enter / `onPointerUp`; `DocOp[]` + one `applyBatch(ops,'user')` in each of the four multi-item loops (pass the source explicitly — it defaults to `'agent'`); guard the task-move commit with `snappedDelta !== 0`. One detail: `applyOps` is all-or-nothing, so filter the selection against the live document before building the batch.
- **B — A transaction boundary in the store.** `beginTransaction()` / `commit()`, with `mutate` merging into the open frame; every interaction — typing, slider, drag, bulk op — opens one. History stores ops rather than whole documents (`docOps.ts` already exists and is already the agent's path). Frames are labelled, the undo button says what it will pop ("Undo — moved 12 packages +7d"), and the frames list in the palette so a planner can jump back to "before Monday's re-baseline".
- **B costs** a store-wide invariant that every future interaction has to honour, plus the label strings; A costs nothing new but has to be re-applied by hand to every interaction added later.
- **Recommend A now, B when the inspector lands.** A is a half-day and removes the data-loss risk today; B only pays for itself once there are many more edit surfaces, which is exactly what theme 3's option B creates.

## 5. Nothing owns the file, and nothing reports what happened to it

**Root cause.** The product's premise is that the HTML file *is* the plan, and no component owns that fact. The save target is module-level state in `fileIo.ts:40` that nothing ever clears and nothing persists; the dirty flag exists (`documentStore.ts:30, :147, :261-263`) and is read only by two guards; and there is no announcement channel at all — a grep for `toast|aria-live|snackbar` over `src/` returns nothing.

**Absorbs (safety):** the stale handle overwrites the plan you just left — File > New roadmap… then the habit Ctrl+S writes a blank roadmap over `programme.html` with no picker and no warning (blocking) · the palette's Open still replaces unsaved work without asking, and its Save never calls `markSaved`, so the flag it leaves behind makes the File menu's new confirm fire on a plan that is safely on disk · crash recovery is dead in every file you have saved (the embedded document always wins, and the debounced autosave then overwrites the newer snapshot within 800ms of reopening) · closing the tab loses unsaved work with no `beforeunload` · Ctrl+S re-asks where to save in every session, and on Firefox/Safari — or on any cancelled picker — silently drops another copy in Downloads · a failed save produces nothing on screen, and `verifyWritePermission` exists but is only called by the updater · opening a file that is not a roadmap does literally nothing in Chrome and Edge, the only browsers where saving works at all · "Delete section and its rows" is unstyled, unconfirmed, and does not delete the rows — the children keep a `groupId` pointing at a deleted parent and stay visible.

**Absorbs (reporting):** the app never says which file you are editing or whether it saved — identical silence for "saved" and "did nothing", and `markSaved` currently fires even on a cancelled save · `Capture baseline` is observably indistinguishable from doing nothing, because `showBaseline` defaults false · every export produces no receipt · every template starts five months in the past, and the brand-new New-roadmap dialog hands them out · loading a plan keeps the old pan and zoom, so a 2027 plan can come up on an empty screen.

**Choice.**
- **A — One status line, one `detachFile()`.** Export `detachFile()` from `fileIo.ts` and call it from `NewRoadmapDialog` and the template path. Add the dirty-confirm helper to the palette's Open and `markSaved()` to its Save. Have `saveToFile`/`saveAs` return whether bytes were written, so `markSaved` cannot fire on a cancel. One polite `role="status"` region in the status bar — the dev agent chip at `StatusBar.tsx:37-42` is the pattern — that every action writes one sentence to: "Saved 14:32", "Save failed — use Save as…", "Not a PowerRoadmap file: notes.html", "Baseline captured for 33 packages", "plan.png exported", "Deleted 14 packages · Undo". The bound file's `name` beside the TitleChip with a dirty dot. A `beforeunload` while dirty. Re-anchor templates in `build` by shifting all four dated collections by `diffDays(min, todayISO())`. Reset `didInitialFit` on a load counter.
- **B — A document bar.** The file becomes a first-class object: the store holds `{doc, fileHandle, savedRevision}`, so the save target travels with the plan it belongs to; the handle persists in IndexedDB keyed by document, re-granted on the first Ctrl+S via `verifyWritePermission` under the keystroke's user activation; the header shows the file name, full path on hover, save state with a timestamp, a recent-files list, and "Not saved to a file — autosave only" in the state every first run is in; per-document autosave with the last few snapshots, so reopening offers "a newer unsaved version from Tuesday 16:40"; Open goes through `replaceDocument` so Ctrl+Z brings the previous roadmap back and no prompt is needed.
- **B costs** IndexedDB handle storage with its permission dance, a v2 autosave key with a v1 fallback, and a visible header surface the owner has to like. (A second *open document* is not on the table either way: the save format embeds exactly one `powerplanner-data` tag.)
- **Recommend A, then the handle-persistence half of B.** A removes the overwrite and the silence in a day; re-picking the save path every single session is the one remaining insult that A does not touch, and that is the half of B worth buying.

## 6. Collapse to seven lines and the plan says nothing

**Root cause.** A group is not an object. It is a bare entry in a flat `doc.rows` array plus a `groupId` on its children, so no operation treats a stream as a unit: `moveRow` steps a block past exactly one *row*, which is the next section's header; `addRowBelow` inserts into a group's child slot with `groupId: null`; and the roll-up derived at `engine.ts:201-216` is min(start)/max(end) and nothing else — no progress, no colour, no milestones, no tasks on the group row itself, one nesting level.

**Absorbs:** Move up / Move down on a section interleaves two streams in one click, and leaves `groupId` disagreeing with visible position, so the gutter draws a package under the wrong spine and collapsing one group removes rows from the middle of another (blocking/often) · "Wrap in a new section" on an already-grouped row silently removes it from its old stream · Insert ▸ Row and the palette's New row append to the very end as top-level, and there is no "New section" command anywhere · a group header is not a handle for its contents — clicking "Platform — BSW and MCAL" yields a one-item selection and a bar with three buttons, one of which silently does not render · Insert ▸ Task files the task on `rows[0]`, a group header, where its bar collides with the roll-up — the behaviour D7 already records as a defect · the roll-up bar is a 6px grey stub with no progress and no stream colour, while the gutter spine beside it is coloured (two findings, one root) · nothing on the chart distinguishes at-risk from on-track, and the critical-path outline uses the same red token as the today line and deadline markers · baseline slip is a 3px grey stub positioned 8px below its own bar, with no direction and no day count, off by default and absent from the sample · bulk recolour does not exist, although colour is the stream tag · a nested section renders wrong and cannot be repaired by hand.

**Why #6 and not lower.** Collapsing to seven lines is the natural move on a 40-row plan and it is how the chart gets presented. Those seven lines currently carry a faint grey date bracket and nothing else, and one right-click on the wrong menu item scrambles the document with no warning.

**Choice.**
- **A — Make the group row correct.** Step by whole blocks in the caller (`ChartContextMenu.tsx:121-134`), clamping a child's step to its own section's range; leave the reducer alone, its semantics are already pinned by `tests/unit/rowOps.test.ts:50-54`. `addRowBelow` sets `groupId: row.id` when the selected row has children; disable "Wrap in a new section" on an already-grouped row; add a "New section" button. Target the first non-header row from all five insert call sites, and group `RowSelect`'s options with `<optgroup>`. Lift the group-colour derivation out of `RowGutter`'s private `useMemo` into the engine, add `color` and `percentComplete` to `SummaryBar`, accumulate duration-weighted progress, walk descendants transitively and include tasks on the parent's own row; draw the summary as a coloured track with a filled portion and the percentage inside. Give the critical outline its own `--color-critical` token; position the baseline ghost immediately under the drawn bar and colour it by direction; make `captureBaseline` turn `showBaseline` on the first time. Row-click selects the whole subtree's bars. Bulk recolour in `MultiFields` through one batch.

## 7. The axis is a ruler that disagrees with the view

**Root cause.** `calendar.scale` and `pxPerDay` are two independent sources of truth. `setScale` writes only the enum, so the five scale buttons relabel the axis without zooming; the axis then draws each tier as a row of *points* whose leading tick sits at a negative x and is clipped away — and that leading tick is the one carrying the year. The viewport origin is an ISO date, so pan and zoom are quantised to whole days.

**Absorbs:** D/W/M/Q/Y buttons, their five shortcuts and their five palette commands do not zoom, so the only working zoom is Ctrl+wheel, +/− and Home-fit; zoomed tighter than a year, pressing Q also empties the major band · the leading month/quarter label is clipped, so any view that does not straddle a January states no year anywhere, defeating SRS-TAX-025 and the expectation pinned at `tests/unit/timeAxis.test.ts:67-72` · no vertical reference runs from the calendar into the plot — the plot is 1656px of blank field, and the grid drags snap to is never drawn · no way to return to today or jump to a date; Today is reachable only by Home, which throws away the zoom, and Home itself hardcodes a 200px gutter the user can drag to 520 · the minimap stacks all 33 packages on one 10px line, shows no dates, no today, no milestones, lands ~11 days off at the right-hand end, and cannot be dragged — and it is on by default · Ctrl+wheel slides the week out from under the pointer and Shift+wheel is inert at fine zoom · axis label thinning uses fixed pixel gaps rather than text width, so month labels overlap at common zooms (PLAN.md:684 already carries the measurement) · the FY year band labels a Jan–Dec span "FY2026" directly above "Q4 2025".

**Choice.**
- **A — Make the scale a zoom, pin the labels, draw the grid.** `setScaleZoom(scale, widthPx)` beside `fit`, setting pxPerDay per band while holding the centre date, called from all three sites. Draw the major label at `max(4, t.x + 8)` and the minor at `max(2, t.x + 4)` so the leading label survives the clip, and skip the thinning test against `ticks[0]` when its x is negative. Thin on measured text width instead of constants. Emit the already-computed tick x positions as full-height rules in a group before the body. `goToToday(widthPx)` on a Today button in the command bar's pinned group and a palette command, plus a clickable chevron when today is off-screen; replace Home's hardcoded gutter. Give the minimap a lane per row from `rowOffsets`, milestone ticks, a today line, quarter labels, and fix its hit maths through `getScreenCTM().inverse()`. Label the FY band from `fiscalQuarterOf` so the two bands cannot disagree.
- **B — A calendar, not a ruler.** The major band becomes a run of labelled *cells* — one rect and one centred text per month/quarter/year, clipped to the viewport, name centred in the visible part, hairline at each true boundary — so the current period is unmistakable at any pan position and the year never has to be smuggled onto a leading tick. `buildAxis` picks its two populated tiers from pxPerDay alone and D/W/M/Q/Y become true zoom presets ("fit one quarter to the window"); `calendar.scale` stays in the document as the drag-snap unit and the embed renderer's field but stops deciding what the axis shows. The viewport origin becomes a float interval `[t0, t1)` in days, so zoom anchors exactly at the pointer, pan is pixel-smooth, and an axis sweep lands on exactly the range swept. A date-navigation group: Today, a period stepper, and a date field accepting "today", "Q1 26", "2027-03".
- **B costs** a rewrite of `buildAxis`'s tier selection and of the viewport store's unit, which touches every x computation in the app and the axis-sweep commit; and it retires SRS-TAX-025's year-on-the-leading-tick compromise, which is a spec amendment.
- **Recommend B for the axis band, A for everything else.** The cell-based header removes three findings at once (clipped label, missing year, FY contradiction) and is the only version where the five scale buttons can stop lying; the float viewport can wait.

## 8. The keyboard and the one page that teaches it disagree with the app

**Root cause.** Bindings live in an if-chain in `useKeyboardShortcuts.ts` where a bare-letter branch can win a chord and `return` before the chord block is reached, and the shortcuts overlay is a separately hand-maintained table.

**Absorbs:** the documented `⇧ M → Month` never reaches the scale block — it adds a milestone on `rows[0]` at today's date, usually outside the fitted window, and it reaches the exported PNG; Ctrl+N does the same with a task; Shift+B is the same latent shape · the overlay teaches `Wheel → Zoom at cursor` when a plain wheel scrolls rows, and the axis sweep — one of the two gestures that actually moves a 40-line roadmap — is taught nowhere and has no cursor · Ctrl+K is the app's menu bar and only the never-seen empty state mentions it, and critical path and baseline drift have no route outside it · F2 is documented unqualified and works only on tasks, while rows rename three different ways with two different commit semantics (one of them a `window.prompt`) · ⌘ glyphs on three teaching surfaces with "Ctrl" on the tooltips an inch away · the overlay does not trap keys, so trying one while reading it adds a milestone or deletes the selection.

**Choice.**
- **A — Fix the chain and the table.** Add `&& !meta && !e.shiftKey` to the `'n'`, `'m'` and `'b'` branches. Correct the overlay's Navigation group to the shipped bindings and add the axis sweep; set `cursor: 'ew-resize'` on the two axis band rects. Extend F2 to a selected row (lifting `RowGutter`'s `editing` into `editStore`) and replace the `window.prompt` with the same `InlineLabel`. One `mod` helper returning `Ctrl`/`⌘`. A `modalOpen` flag the overlay sets and `useKeyboardShortcuts` checks. A `⌘K / Ctrl K — Search commands` row plus a search chip in the header, and Critical path and Baseline as `aria-pressed` toggles in the command bar's document group.
- **B — One keymap table.** Every binding declared once as `chord + label + handler`, matched on the full chord so a bare letter cannot shadow one; `useKeyboardShortcuts`, `useChartInteractions` and `ShortcutsOverlay` all read it; modifier rendering comes from the same declaration so Ctrl/⌘ cannot diverge; a unit test asserts no two entries shadow each other and that every registered chord and gesture has a label. The overlay becomes a live cheat-sheet: rows highlight as their chord arrives, with the current tool echoed in the footer, document-mutating branches suppressed while it is open.
- **B costs** a refactor of two hooks that nothing else is asking for, and a convention every later binding must follow.
- **Recommend B.** Three separate findings in this theme exist only because the table is hand-maintained, and the keymap is the single cheapest structural fix in the audit — an afternoon that permanently closes a class of bug, versus A's four patches that the next binding reopens.

## Parity gaps against the agent bridge (SRS-ABR-019 — a rule, not a preference)

`spec/srs-web/SRS-agent-bridge.md:37`: *"Every document operation available to an agent shall also be reachable by a user through the UI, without the bridge."* Owner directive 2026-10-23. These are violations, so they are not subject to an A/B choice.

| # | Operation the bridge can perform | Why a user cannot reach it |
|---|---|---|
| 1 | `set_holidays` | Declared `documentStore.ts:88`, implemented `:212`, no caller in `src/app` or `src/renderer`. The calendar popover offers only fiscal year and working days (`CommandBar.tsx:223-282`). Compounding: `calendar.holidays` is read nowhere but schema validation, so an entered holiday would not be shaded either (`ChartArea.tsx:130-142` uses `workingDays` only). The bridge accepts it regardless — `DOC_OP_SCHEMA` is `additionalProperties: true` (`mcp/agent-bridge/server.mjs:51-57`). |
| 2 | `update_milestone.label` | Inline rename exists only for tasks (`editStore.editingTaskId`) and rows. `ChartContextMenu.tsx:214` offers an item literally labelled "Edit label" that only calls `setSelection`, and `SelectionGroup.tsx:71-73` then shows a dead span whose tooltip says "rename it in the row list" — milestones are not in the row list. |
| 3 | `update_bracket.label` | `BracketFields` (`SelectionGroup.tsx:267-286`) has start and end only; the bracket title text is `pointerEvents="none"` (`Brackets.tsx:74`); the menu item at `:237` honestly says "Select, to edit in the bar", and the bar then has nothing to edit. |
| 4 | `update_marker` — entirely (label, date, colour) | `Markers.tsx:19-31` emits no `data-pp-kind`/`data-pp-id`, so `target.closest('[data-pp-kind]')` can never resolve to a marker; `SelectionGroup.tsx:52` returns `null` for one anyway, so the command bar's left group would be empty. `doc.markers` is consumed nowhere else in the UI, so there is no list to reach one from either. |
| 5 | `update_milestone.color`, `update_bracket.color`, `update_marker.color` | All three fields exist (`document.ts:55, :64, :81`) and all three render (`Milestones.tsx:46`, `Brackets.tsx:27`, `Markers.tsx:16`). `ColorPalette` is mounted exactly once, in `TaskFields` (`SelectionGroup.tsx:199`). |
| 6 | `update_bracket.rowIds` | `BracketFields` has no row-span control and the bracket drags (`useChartInteractions.ts:392-408`) move dates only. |
| 7 | `update_dependency.from` / `.to` | `ChartContextMenu.tsx:245-251` offers `type` only. Re-pointing a mis-drawn link means delete and re-drag between two 10px dots. |
| 8 | `update_row.groupId` on a section | Every grouping item is gated behind `if (!isSection)` (`ChartContextMenu.tsx:137`), so a section can never be re-parented — which is also the only way to repair a nested structure an agent or a hand-edited file created. |

Adjacent, outside the document-op wording but the same dependency: `set_viewport` (`src/agent/AgentBridge.ts:266-269`, exposed at `mcp/agent-bridge/server.mjs:131`) lets an agent jump the view to a date; a human has Home-fit and a click on a broken minimap. And `select` + `delete_marker` are reachable for the bridge (`AgentBridge.ts:289`) while unreachable for a person, which is why #4 is a trap rather than merely a gap.

The smallest closing set: generalise `editStore` to `{kind, id}` and mount the existing `InlineLabel` in `Milestones.tsx` and `Brackets.tsx` (closes 2 and 3 and makes three dead menu items honest); add `data-pp-kind="marker"` plus a transparent 10px hit line and a `MarkerFields` branch (closes 4, and marker colour); add `ColorPalette` to `MilestoneFields` and `BracketFields` (closes 5); add a row-span picker to `BracketFields` (6); make a selected dependency's endpoints re-draggable (7); drop the `isSection` gate on re-parenting (8); add a holidays date-list beside the working-day toggles **and** the matching shading (1 — without the shading the field is still invisible). Worth buying with it: a test that enumerates every `DocOp` variant in `docOps.ts:32-59` and fails on any whose UI path is unregistered, so a new field in `src/types/document.ts` cannot open a gap unnoticed. Not worth buying: a schema-generated inspector — AGENTS.md's direct-manipulation convention means a bracket's row span wants handles on the chart, which a generated form cannot produce.

## Not carried forward

- **FY year band labels a Jan–Dec span "FY2026"** — real and proven from the code, but needs a non-January fiscal year *and* a quarter/year scale to bite; the one-line fix is named inside theme 7-A, and it drags SRS-TAX-011 and a pinned test with it, so it should ride along with the axis work rather than be decided on its own.
- **A nested section renders wrong and cannot be repaired by hand** — no UI path can create the state; it is reachable only through the bridge or a hand-written file. The defensive half (reject a `groupId` naming a row that itself has one, in `docOps.ts` and `schema.ts:62-63`) is worth a line in a hardening pass, not an owner decision.
- **Seven stream colours carry meaning with no legend** — the planner knows their own streams and the colour is largely redundant with position under the group header; the cost lands only in an export crop, and the fix overlaps DECISIONS.md D4, which parks presentation export.
- **Pan is the default background drag** — D7 already settles the idle-only tool row as an accepted trade, and which gesture owns the background drag is a preference. Only the verifiable halves are carried: the cursor stating no gesture (theme 1) and the marquee's unconditional `sel.clear()` (theme 1).
- **`Task` has no owner field** — real and one line to add, but a stream-coloured programme chart already encodes the owning discipline in the bar colour, so this is a convenience; it rides inside theme 3 rather than earning a choice.
- **On-bar labels are fixed ink over a fully saturated fill** — two bars in the shipped sample sit at ~1.8:1 contrast, so it is genuine, but the fix needs a luminance computation and a special case for the literal string `var(--bar-default)`; it belongs in whichever pass touches `LabelText`, which is theme 3-B's "decide what the plot area is for".
- **Axis label thinning uses a fixed gap, not text width** — carried inside theme 7-A as one of the label fixes, not raised as its own choice; PLAN.md:684 already tracks it as L0g with the measurement.
- **The shortcuts overlay does not trap keys** — carried inside theme 8 as the `modalOpen` flag; it is one boolean and needs no decision.
- **"No snapping to neighbours, milestones or today"** and **"Reordering rows costs one right-click per position"** were already folded by the verifier into theme 1-B and theme 6 respectively; they are named here so the count reconciles.
